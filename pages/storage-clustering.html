Clustering & Search Optimization
Two complementary techniques for accelerating queries on large tables — automatic clustering for range scans, and the Search Optimization Service for point lookups.
Use Clustering when
Table is >1 TB and queries always filter on the same 1–2 columns (date, region, tenant)
Data is inserted out of order relative to your filter columns
You see high partition scan counts despite reasonable predicates
Skip Clustering when
Table is <500 GB — micro-partitioning already prunes well
Queries filter on many different columns with no dominant pattern
Table is append-only with natural time-order (already well-clustered)
Choosing a Cluster Key
Pick columns that appear most often in WHERE clauses and have moderate-to-high cardinality. Low-cardinality columns (e.g. boolean) provide little benefit; too-high cardinality (UUID) spreads rows too thin.
CLUSTER BYcardinalityfilter patterns
Automatic Reclustering
Once a cluster key is defined, Snowflake monitors clustering depth and triggers reclustering serverlessly in the background as DML causes disorder. No manual ALTER or rebuild commands needed.
ServerlessBackgroundZero maintenance
Monitoring Clustering Depth
SYSTEM$CLUSTERING_INFORMATION returns average depth and average overlaps. Lower depth = better pruning. Track reclustering credit consumption via AUTOMATIC_CLUSTERING_HISTORY.
SYSTEM$CLUSTERING_INFORMATIONavg_depth
Clustering Cost Model
Reclustering consumes serverless credits proportional to the data volume reorganized. Balance reclustering savings (less scan cost) against reclustering spend. High-churn tables may recluster frequently; append-heavy tables rarely need it.

Use Search Optimization when
Queries look up individual rows by high-cardinality key (email, order_id, user_id)
Equality or range predicates on columns that are NOT the cluster key
ILIKE / LIKE substring searches on large text columns
vs. Clustering
Clustering = range scans on ordered columns (date ranges, regions)
SOS = point lookups on any column, independent of physical order
They complement each other — a table can have both
Equality & Range Lookups
SOS builds access paths for equality (=, IN) and range (<, >, BETWEEN) predicates on high-cardinality columns. Queries are unchanged — Snowflake automatically uses the access path when it helps.
EQUALITY(...)RANGE(...)Transparent
Substring & VARIANT Search
Enable substring search for LIKE '%term%' and ILIKE patterns on text columns. Also supports equality lookups on VARIANT sub-field values without full JSON extraction on every row.
SUBSTRING(...)LIKE / ILIKEVARIANT paths
Setup & Management
One ALTER TABLE command enables SOS on specific columns and access types. Snowflake builds the access paths offline — no table lock, no impact to queries during build. Disable per-column to control storage cost.
ALTER TABLEADD SEARCH OPTIMIZATION ON
Monitoring & Cost
SOS builds access paths incrementally, consuming serverless credits. Monitor build progress and query acceleration via SEARCH_OPTIMIZATION_HISTORY and EXPLAIN plans — look for "Search Optimization: YES" in the plan output.
